Docker inspect реального контейнера, сохранённое тело create-запроса, bootstrap-скрипт и логи провайдера не предоставлены. Внутренняя реализация CloudCompute не объявляется установленным фактом.

## 4. Итоговая цепочка запуска

1. Сайт до платного POST сохраняет отдельный случайный 64-hex токен движка. CloudCompute API key не передаётся в контейнер.
2. POST /instances явно передаёт `worker` и короткий onstart. Остаются прежние проверки цены, диска, доступности образа и защита от повторной аренды.
3. Onstart запускает существующий `autostart-image.sh --provision`. CMD образа остаётся tini → тот же супервизор.
4. Создаются config/logs/runtime/models; приватные папки имеют 0700, токен — 0600. Запись атомарна, provisioning сериализован. Модели/пользовательские файлы не удаляются и не подвергаются рекурсивному chown.
5. При отсутствии владельца блокировки супервизор запускается через nohup + setsid с закрытым stdin. Повторный такой же запрос не создаёт второй launcher. Новый токен вызывает один перезапуск.
6. Прежний launcher выполняет GPU preflight, запускает прежний FastAPI и прежний Cloudflare tunnel. HMAC rendezvous адреса и этапы сохраняются.
7. Если через 90 секунд нет ни одного сигнала/адреса, сайт пробует поддерживаемую автоматизацию веб-терминала: максимум три попытки исполнения, не чаще раза в минуту. HTTP 409 «терминал ещё не готов» и 429 не расходуют этот бюджет; ожидание ограничено общим timeout, Retry-After учитывается. Это **не повторная аренда**. При bootstrap-ошибке/остановленном инстансе попытки не продолжаются.
8. Initialize Engine выполняет этот же путь по нажатию. Одновременные запросы объединяются, токен существующего инстанса сохраняется. Adopt также пытается запустить его сразу.
9. Супервизор подтверждается отдельно от health. GPU READY не выдаётся по одному статусу CloudCompute либо успешному коду provisioning.

Выключение foreground CMD, ожидающего фонового супервизора, передаёт SIGTERM владельцу в той же PID namespace. Супервизор завершает launcher, а тот — tunnel и FastAPI. Существующий механизм контейнера не заменяется новым сервис-менеджером.

## 5. Терминальный fallback: границы гарантий

Используется исключительно официальный endpoint конкретного instance ID. Клиент поддерживает ttyd, требует TLS и адрес в домене CloudCompute на стандартном порту. URL/токен терминала не сохраняются и не показываются; CloudCompute API key используется только при запросе URL. Перед отправкой токена движка клиент отключает echo/history и ждёт отдельного подтверждения. Секрет не передаётся через argv. Timeout, отказ, неверный URL/протокол и ненулевой код явно показываются пользователю.

Протокол CloudCompute в живой сессии #10766 **не проверялся**. Если провайдер вернёт другой WebSocket host/протокол, потребуется адаптация; система не ослабляет проверку адреса автоматически. При недоступной автоматизации остаётся одна команда «Резервная команда» для browser terminal выбранного инстанса. Она отключает history/echo, вызывает конкретный файл и показывает код завершения. Пользователю не предлагается искать Docker-контейнер, ставить Python либо менять CUDA.

Образ 1.7.7 содержит совместимый `--provision`: сайт может попытаться запустить уже существующий инстанс без пересоздания. Новые исправления самого shell supervisor доступны **только в образе 1.7.7.1**; сайт не объявляет старый контейнер обновлённым и не заменяет его код тайком.

Если CloudCompute игнорирует и CMD, и onstart, а терминал недоступен, Dockerfile сам по себе не может выполнить код. Такое состояние требует восстановления поддерживаемого bootstrap у провайдера. Абсолютная автоматизация во всех внутренних сценариях провайдера не гарантируется.

## 6. Состояния и диагностика

- Running — классифицированный статус провайдера; raw status, включая число 0 или 1, хранится отдельно.
- Запуск сервера — наблюдаемый этап SERVER_READY/локальные сведения; это ещё не готовность соединения.
- Engine ready — проверенная связь с нужным движком. READY TO GENERATE дополнительно использует уже существующую проверку совместимого checkpoint.
- Неизвестные числовые коды остаются UNKNOWN. Из опубликованной документации нельзя честно вывести `1 = running`. Известное сопутствующее строковое поле actual_status/state может дать независимое подтверждение.

Диагностический JSON содержит instance ID, версию сайта, requested image и фактически наблюдавшуюся image_version (если доступна), bootstrap profile, запрос/завершение provisioning, наличие четырёх каталогов, блокировку супервизора, health, доступные GPU сведения, последнюю известную ошибку и время наблюдения. Snapshot передаётся через подписанный rendezvous либо защищённую терминальную сессию. Если данных нет, выводится unavailable; факт запроса не превращается в факт выполнения. Ключи/токены, auth headers, приватные ключи и onstart исключаются, строки дополнительно редактируются.

## 8. Непроверенное и следующий приёмочный запуск

Не установлены: точный create payload #10766, реально выбранный profile, исполнение его onstart, внутренняя логика `/.launch`, живой ttyd proxy провайдера и работа 1.7.7.1 с RTX 3090. Нет доступа к оплачиваемому инстансу и его секретам; новая аренда не выполнялась.

Публикация новым тегом должна выполняться из приложенных исходников после прохождения `tests/docker-startup-1771.sh`. Workflow собирает кандидат, проверяет runtime на CPU, затем публикует и проверяет анонимный манифест. Docker runtime gate в этой среде не запускался: Docker daemon отсутствует, capabilities = 0, установка/namespace операции ограничены. После публикации нужен реальный приёмочный запуск worker + onstart: подписанное provisioning → supervisor → GPU preflight → FastAPI → tunnel → authenticated health → загрузка модели → генерация → повторное Initialize без рестарта → перезапуск сайта с восстановлением связи.

**Это исходники исправления с выполненной локальной проверкой, а не свидетельство завершённой облачной/GPU приёмки.**
