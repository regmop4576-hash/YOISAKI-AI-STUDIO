# YOISAKI v1.8.1 SMART FACE FIX — отчёт по ресурсам

Среда разработки: 4 CPU, без CUDA (`torch.cuda.is_available() = False`), Python 3.13, PyTorch 2.6.0, Diffusers 0.36.0, OpenCV 4.11.0. **Tesla T4 и полноразмерный Illustrious отсутствовали. Чисел VRAM, скорости Colab и пиков SDXL на T4 в этом отчёте нет.**

## 1. Что сохранено без изменений

- Одна FIFO-очередь (`ThreadPoolExecutor(max_workers=1)`) и `InferenceAdapter.lock` для всех SDXL-задач.
- Один набор UNet / VAE / двух text encoder на checkpoint; `from_pipe(torch_dtype=None)` для Inpaint-view с проверкой storage pointers; кэш модели и VAE; LoRA на тех же модулях.
- CPU Offload, VAE slicing/tiling, allocator RAM FIX (`allocator_policy.py` не изменён), MemoryLog, Memory Profiler, result ACK, очистка после отмены/ошибки.
- Новых вызовов `torch.cuda.empty_cache()` нет. Checkpoint не перезагружается между задачами Face Fix.

## 2. Детекция лиц: только CPU, вне GPU-очереди

- Детекторы — OpenCV (LBP-каскад 247 КБ, YuNet 233 КБ). Загружаются **лениво** при первом `POST /facefix/detect` (или при повторной проверке внутри `/generate`), кэшируются в процессе. При старте сервера не загружаются. При установке Colab выполняется однократная проверка загрузки в отдельном подпроцессе `bootstrap`.
- Детекция не импортирует torch и не обращается к CUDA (проверено: `torch_imported: false`). Поэтому одновременная резидентность детектора и SDXL в VRAM исключена.
- `POST /facefix/detect` выполняется в пуле потоков FastAPI с собственной блокировкой (одна детекция за раз), **не** в SDXL-очереди: пользователь видит лица, даже пока идёт генерация (проверено тестом при занятом воркере). Внутри задачи Face Fix повторная детекция выполняется последовательно перед первым проходом SDXL.
- Временные массивы удаляются после детекции; идентификатор изображения считается по уже созданному BGR-буферу без дополнительной копии (на 3072×3072 это экономит ~37 МБ на запрос).

Накопления от повторных детекций не наблюдалось (20 повторов: 410 → 336 → 341 МиБ). Это CPU RAM; на T4/Colab не измерялось.

## 3. Исправление нескольких лиц

- Одна задача `/generate` → повторная детекция → для каждого выбранного лица по очереди: crop + маска → тот же `StableDiffusionXLInpaintPipeline`-view → композит → результат становится исходником для следующего лица. Промпт кодируется один раз на задачу. Параллельных SDXL-вызовов нет.
- Прогресс охватывает все лица: `total_steps = int(steps × denoise) × число лиц`; ETA и отмена работают на всём диапазоне. Отмена проверяется в callback каждого шага; при отмене во втором лице `finally` закрывает все временные изображения и возвращает базовый pipeline.
- Минимальная проверка RAM (`check_budget`) не изменена: оценивает исходник, результат, маску и рабочий RGB; при многолицевой обработке одновременно живут текущий результат и один crop.

## 4. Диагностика

- `/jobs/{id}` и `/memory` → `job_resources` для Face Fix содержат блок `face_fix`: детектор, запущенные детекторы, число найденных лиц, время повторной детекции, число запрошенных и реально исправленных лиц, плюс прежние поля (время задачи, RAM/VRAM до и после cleanup, пики аллокатора CUDA, выборочный пик RSS, model_reused, тип pipeline, исход cleanup).
- `/memory` → `face_detection`: последняя детекция — детектор, число лиц, длительность, загруженные модели, RSS и CUDA allocated до/после.
- В логи не пишутся изображения, промпты, токены и OAuth-данные. Последняя ячейка блокнота скачивает `YOISAKI_RESOURCES_V1.8.1.zip`.

## 5. Что проверить на T4

1. Smart Face Fix на одном изображении 5–10 раз подряд с тем же checkpoint/LoRA → сравнить RSS и allocated VRAM после cleanup (последняя ячейка).
2. «Исправить все» на изображении с 2–3 лицами; затем отмена во время второго лица и следующая задача.
3. Рабочий размер 1024 против 768: время на лицо и пик VRAM; при OOM — уменьшить «Рабочую ширину/высоту» в расширенных настройках (автоматически ничего не уменьшается).
4. Text2Img → Img2Img → Inpaint → Smart Face Fix в одной сессии.
