# YOISAKI ENGINE · CloudCompute Deployment Edition 1.7.1 — технический отчёт

**Исходные данные:**

- `YOISAKI_AI_STUDIO_V1.7.0_IMG2IMG_EDITION.zip`;
- `YOISAKI_ENGINE_V1.7.0_IMG2IMG_EDITION.ipynb` — побайтно совпадает с копией в ZIP;
- `YOISAKI_V1.7.0_IMG2IMG_REPORT.md`.

**Цель:** запускать тот же YOISAKI ENGINE на арендованном GPU CloudCompute.ru и управлять им только с Android-телефона. Google Colab остаётся рабочим вариантом.

**Главный итог проверки.** На машине без NVIDIA GPU проверено следующее:

- сборка Docker-образа;
- полный набор Python-тестов (прежние и новые) на закреплённом стеке внутри образа;
- запуск настоящего сервера движка через launcher;
- авторизация, `/health`, остановка, хранение и загрузчик моделей.

**Ни одна генерация на реальном GPU CloudCompute не выполнялась.** Туннель Cloudflare в песочнице недоступен (нет DNS для `api.trycloudflare.com`). Список проверок, для которых нужен арендованный GPU, — в разделе 10.

## 2. Сведения о CloudCompute и что осталось непроверенным

Страницы cloudcompute.ru из среды разработки **недоступны**: прокси песочницы отвечает 403 на CONNECT `cloudcompute.ru:443`. Поэтому сведения ниже взяты из поисковой выдачи по официальным страницам (FAQ, главная, глоссарий, changelog), а не из полного текста документации:

**Подтверждено фрагментами официальных страниц:**

- можно запускать свои Docker-образы или готовые шаблоны;
- на GPU-инстансах предустановлен NVIDIA Container Toolkit, флаг `--gpus all` работает;
- доступ по SSH, RDP или через веб-интерфейс, в зависимости от конфигурации; при создании добавляется SSH-ключ;
- почасовая тарификация, без минимального срока;
- при нулевом балансе инстансы останавливаются, но не уничтожаются; данные остаются; **хранение продолжает оплачиваться до удаления или перевода в offline**;
- режим on-demand или interruptible фиксируется при создании;
- в панели есть журналы контейнера и системные журналы;
- статья CloudCompute о бэкапах предупреждает, что копия на том же диске инстанса не защищает от его удаления.

**Не удалось проверить (учтено в реализации):**

| Вопрос | Как учтено |
|---|---|
| Инстанс — это ВМ с Docker или сам контейнер. | Автоматический выбор режима: `docker` или `native`. |
| Точный путь постоянного диска (например, `/workspace`). | Путь настраивается (`YOISAKI_DATA_ROOT`). Есть метка `.yoisaki-data-id` и инструкция, как проверить сохранность. |
| Открыты ли входящие порты. | Входящие порты не нужны: используется только исходящий туннель. |
| Семантика entrypoint у собственного образа. | Образ запускается с `tini` и launcher. Если платформа подменит команду, `start-cloudcompute.sh` работает и внутри образа (`YOISAKI_IN_IMAGE=1`). |
| Версия драйвера на хостах и сохранение диска при переносе инстанса. | Проверка GPU перед запуском; предупреждения в инструкции. |

Цены и наличие RTX 5060 Ti (около 23 ₽/ч, 32 ГБ RAM, 944 ГБ диска) — наблюдения пользователя, а не гарантия. В пакете они не используются.

## 3. Архитектура

```
Android Termux: YOISAKI AI STUDIO (без изменений)
      │ HTTPS, Bearer-токен (как с Colab)
      ▼
https://<случайное>.trycloudflare.com  ──(исходящий туннель cloudflared 2026.9.3, SHA-256)──┐
                                                                                            ▼
CloudCompute GPU-сервер ── cloudcompute/launcher.py (супервизор, только stdlib)
                              ├─ diagnose.py --gpu-check   (ядра PyTorch для sm_XX + пробный fp16 matmul)
                              ├─ engine/worker/serve.py    (НЕИЗМЕНЁННЫЙ движок 1.7.0, 127.0.0.1:8765)
                              └─ cloudflared tunnel --url http://127.0.0.1:8765
     Режим docker: всё это внутри контейнера yoisaki-engine (uid 1000, read-only rootfs)
     Режим native: venv в $YOISAKI_DATA_ROOT/runtime/venv, процесс от пользователя yoisaki
```

Порядок запуска (`launcher.py run`):

1. Создаются только отсутствующие папки. Пользовательские файлы не изменяются.
2. Ставится блокировка `flock`: второй движок с той же папкой данных не запустится, поэтому SDXL не загрузится в VRAM дважды.
3. Проверка GPU. Если GPU не подходит, сервер не стартует, и оплачиваемое время не тратится.
4. Сервер запускается с новым токеном (`secrets.token_hex(32)`) так же, как в `panel.py`, с той же политикой аллокатора `worker_environment`. Launcher ждёт `/health` = `READY`.
5. Сводка по моделям. Если checkpoint нет, выводится предупреждение.
6. Необязательный прогрев (`YOISAKI_WARMUP_CHECKPOINT`): одна настоящая генерация 512×512 в 2 шага с последующим ACK. После него модель действительно загружена.
7. Туннель: URL берётся из журнала cloudflared, затем `/health` проверяется через сам туннель. Только после этого ссылка записывается в `runtime/state/link.txt` (права 0600).
8. Наблюдение:
   - сервер упал → всё останавливается;
   - туннель пропал или 3 раза подряд не ответил на `/health` → новый туннель (до 3 раз). Ссылка при этом меняется, и это выводится в журнал.
9. SIGTERM, SIGINT или SIGHUP:
   1. сначала останавливается туннель, чтобы не принимать новые запросы;
   2. затем сервер (`terminate`, 30 с): uvicorn lifespan движка отменяет очередь и выгружает модель;
   3. токен и ссылка удаляются.

## 5. Совместимость

**GPU и стек.** `torch 2.10.0` — последняя версия на PyPI, у которой стандартные колёса Linux x86_64 собраны с CUDA 12.8 (`nvidia-cuda-runtime-cu12==12.8.90`). Начиная с 2.11 колёса PyPI переходят на CUDA 13 (`nvidia-cudnn-cu13`), а это требует более нового драйвера на арендованном хосте. Проверено на собранном образе: `torch 2.10.0+cu128`, архитектуры `sm_70 sm_75 sm_80 sm_86 sm_90 sm_100 sm_120`.

| GPU | Архитектура | Ядра в сборке |
|---|---|---|
| Tesla T4 | sm_75 | есть |
| RTX 3060 / 3090 / A5000 | sm_86 | есть |
| RTX 5060 Ti | sm_120 | есть |

Для RTX 50xx нужен драйвер хоста с CUDA 12.8 (ветка 570+). Это не предполагается заранее, а проверяется при каждом запуске: `diagnose.py --gpu-check` сверяет `sm_XX` со списком скомпилированных архитектур (или PTX ≤ capability) и выполняет fp16 matmul на GPU. Так ловится `no kernel image is available` до запуска движка.

Остальные пины не менялись: `diffusers 0.36.0`, `transformers 4.57.3`, `accelerate 1.12.0`, `peft 0.18.0` и другие. `pip check` в образе: «No broken requirements found». Python 3.12, как в Colab.

**Google Colab.**

- Блокнот и `engine/` побайтно не изменены. Тест распаковывает `_PACKAGE`, сверяет SHA-256 с `_EXPECTED`, сравнивает все 25 файлов с `engine/` и проверяет, что в блокноте нет упоминаний CloudCompute.
- Новый код лежит в `cloudcompute/` и в корне. Ни один модуль движка его не импортирует.

**Сайт.**

- Не изменён.
- Тест вызывает настоящий `parseTunnel()` из `server/upstream.mjs` для ссылки в формате launcher и получает тот же origin и токен.
- Тексты на странице GPU упоминают Colab. Это осознанно не исправлялось: задание запрещает менять сайт без доказанной необходимости.

## 6. Хранение и быстрый повторный запуск

```
$YOISAKI_DATA_ROOT (по умолчанию /workspace/yoisaki-data)
├── models/{checkpoints,loras,vae,controlnet}   каталог движка (как на Drive); в Docker смонтирован только для чтения
├── huggingface-cache/                         HF_HOME (+ TORCH_HOME): ControlNet, SDPose-OOD, Annotators, Depth, конфиги SDXL
├── sdpose/                                    необязательная локальная копия SDPose-OOD (подхватывается как YOISAKI_SDPOSE_REPO)
├── outputs/                                   YOISAKI_RESULTS_DIR: прежний ResultStore (до ACK + 24 ч, политика движка)
├── logs/                                      launcher.out, server.log, tunnel.log (по одной ротации .1), install-native.log
├── diagnostics/                               memory.jsonl (движок), startup-timings.jsonl, cloudcompute-report.txt
├── config/yoisaki.env                         необязательно; 0700/0600
├── runtime/venv, runtime/bin/cloudflared      только в режиме native
├── runtime/state/                             0700: launcher.json, token, link.txt (0600), launcher.lock
└── .yoisaki-data-id                           метка сохранности диска (пишется один раз)
```

**Что переиспользуется при повторном запуске:**

| Что | Почему не переустанавливается |
|---|---|
| Образ Docker | Метка исходников совпала → нет сборки. Если исходники изменились, при пересборке слои зависимостей берутся из кэша. |
| venv (режим native) | Маркер совпал → нет установки. |
| cloudflared | Только сверка SHA-256. |
| Веса в кэше HF | Повторно не скачиваются: стандартное поведение `huggingface_hub`. При `YOISAKI_HF_OFFLINE=1` нет даже сетевых проверок. |

**Защита данных:**

- `fetch_models.py` не перезаписывает существующие файлы.
- Перед загрузкой проверяется свободное место: размер + 2 ГБ, а без `Content-Length` — не меньше 12 ГБ.
- Загрузка идёт в `*.part` с докачкой через `Range`.
- Заголовок safetensors проверяется кодом каталога движка (`worker.models.inspect`). Повреждённый файл не попадает в каталог и сохраняется как `*.invalid`.
- Токен Civitai или HF добавляется как `unredirected` и не уходит на CDN при редиректе.
- Скрипты ничего не удаляют из `models/` и `outputs/`.

**Шаблоны `prefetch`** совпадают с файлами, которые запрашивает движок:

- шаблоны `sdxl-config` дословно повторяют `diffusers/loaders/single_file.py:251` (diffusers 0.36.0);
- для ControlNet используется `fp16` variant, как в `controlnet.py`;
- репозитории сверяются тестом с исходниками движка.

**Ограничение.** Сохранность диска при остановке, переносе или удалении инстанса определяет CloudCompute. Пакет её не гарантирует, а помогает проверить: метка `.yoisaki-data-id` и раздел 8 инструкции.

## 7. Память

Политика памяти движка **не менялась**: код в `engine/` тот же.

- fp16;
- `enable_model_cpu_offload()` на любом GPU, включая 24 ГБ: автоматического отключения нет;
- VAE slicing и tiling;
- `from_pipe(torch_dtype=None)` для Img2Img и ControlNet;
- жизненный цикл ControlNet и полная выгрузка SDPose-OOD;
- `finish_job()` / `to_base()` после каждого задания, в том числе после ошибки;
- та же политика аллокатора glibc (`YOISAKI_RAM_FIX`, через `worker_environment`).

Блокировка launcher исключает второй процесс движка, а значит и вторую копию SDXL.

Настраиваемые параметры (`config/yoisaki.env`):

- `YOISAKI_RAM_FIX`;
- `PYTORCH_CUDA_ALLOC_CONF` — по умолчанию не задан, как в Colab;
- `YOISAKI_WARMUP_CHECKPOINT`.

Отключение CPU Offload на больших GPU потребовало бы менять движок, поэтому в этот выпуск не вошло. `diagnose.py` предупреждает:

- если VRAM меньше 12 ГБ;
- если RAM или лимит cgroup меньше 16 ГБ;
- если на диске меньше 20 ГБ.

## 8. Безопасность

| Мера | Как реализовано |
|---|---|
| Нет открытых портов | Сервер слушает только `127.0.0.1` (тест проверяет `/proc/net/tcp`). В compose нет `ports`. |
| Аутентификация | Без изменений: Bearer с `hmac.compare_digest` для всех маршрутов. Тест: без токена и с чужим токеном — 401. |
| Токен | Новый при каждом запуске. Есть только в окружении сервера и в файлах `runtime/state/token` и `link.txt` (0600, папка 0700). Не попадает в argv, журналы и `docker logs`: тест ищет токен во всех журналах и выводе. При остановке удаляется. |
| Просмотр журналов | `check-cloudcompute.sh logs` скрывает 64-hex, `#token=` и `Bearer`. |
| Секреты | Не хранятся в Git, compose или образе. `HF_TOKEN` и `CIVITAI_TOKEN` передаются только из окружения или `config/yoisaki.env` (600). Файл настроек разбирается, а не выполняется: `$(…)` не исполняется, `YOISAKI_TOKEN` и `YOISAKI_DATA_ROOT` из него игнорируются (проверено тестом). |
| Привилегии | Без root: uid 1000 в Docker; в режиме native при входе под root создаётся системный пользователь `yoisaki` (`runuser`). Docker: read-only rootfs, `cap_drop: ALL`, `no-new-privileges`, модели только для чтения. |
| Целостность | cloudflared закреплён по версии и SHA-256. Базовый образ закреплён по digest. |
| Без автоматики | Нет автозапуска (`restart: "no"`, нет systemd или cron). Нет операций с аккаунтом CloudCompute, создания инстансов и платежей. |

**Особенности среды проверки** (на поставляемые файлы не влияют):

- Прокси песочницы перехватывает TLS. Для сборки использовался производный `Dockerfile.validate`: к боевому `Dockerfile` добавлен только CA песочницы через `--build-context`. Боевой `Dockerfile` не менялся.
- Для проверки Docker-режима без NVIDIA-драйвера использовался override `compose.validate.yml` (`YOISAKI_COMPOSE_OVERRIDE`): без резерва GPU, с имитацией CUDA и `YOISAKI_GPU_PREFLIGHT=0`.
- Обе заготовки описаны в журналах и в пакет не входят.
- Тест панели Colab требует `ipywidgets` (есть в Colab). Для прогона в образе он ставился как тестовая зависимость вместе с `pytest` и `httpx`.
- Изменения исходников после полной сборки (только `cloudcompute/*.py` и `*.sh`; `Dockerfile`, `requirements` и `engine/` с тех пор не менялись) применялись к образу через `validate/Dockerfile.patch`. Это те же шаги COPY и проверки импортов поверх полной сборки, потому что сеть песочницы упала до 0,2–1,5 МБ/с. Текст файла приведён в `v171-docker-build.txt`.

**Дефекты, найденные проверками и исправленные до выпуска:**

1. `torch.cuda.get_arch_list()` без GPU возвращает пустой список. Проверка ядер переведена на `torch._C._cuda_getArchFlags()`.
2. Корень папки данных принадлежит root, и контейнер (uid 1000) не мог создать метку `.yoisaki-data-id`. Метку теперь создаёт хостовый скрипт, а launcher не падает, если создать её не может.
3. `fetch-models` и `check` в авто-режиме выбирали native на сервере, где движок работает в Docker. Наличие образа YOISAKI теперь означает режим docker.
4. `chmod` чужой папки под `set -e` обрывал запуск. Права теперь меняются только у своих папок, а при отсутствии права на запись выводится понятная ошибка.
5. Отчёт, записанный через `docker exec`, получал права 0666 (umask 000). Во всех точках входа явно задан `umask 022`.
6. Пакет или данные под `/root` (700) недоступны пользователю `yoisaki`. Добавлена проверка доступа с понятной ошибкой.
7. Тесты загрузчика зависели от реального свободного места на диске. Подмена `disk_usage` теперь задана в фикстуре.

## 10. Ограничения и что нужно проверить на реальном GPU

**Не проверено (нет GPU и нет доступа к trycloudflare в среде разработки):**

1. Проверка GPU и fp16 на настоящей RTX 5060 Ti (sm_120) с драйвером хоста CloudCompute; затем на T4 и 3060/3090 при наличии.
2. Создание quick tunnel Cloudflare с инстанса CloudCompute и подключение сайта из Termux.
3. Text2Img и Img2Img с настоящим Illustrious XL, затем LoRA, Regional, ControlNet (OpenPose Classic, SDPose-OOD, Canny, Depth). Пиковая RAM и VRAM по `memory.jsonl`.
4. Какой режим выбирается на реальном инстансе (docker или native) и работает ли `--gpus` / NVIDIA reservation в compose.
5. Сохраняется ли папка данных при остановке и запуске инстанса (метка `.yoisaki-data-id`) и где на CloudCompute лежит постоянный диск.
6. Полная native-установка (`install-native.sh`) и её повторный запуск без действий, а также native-запуск от root с настоящим venv.
7. Время этапов: контейнер → проверка GPU → сервер → туннель, а также загрузка checkpoint и прогрев. **Цифр в этом отчёте нет, потому что они не измерялись.** После первого запуска они будут в `diagnostics/startup-timings.jsonl` и в `./check-cloudcompute.sh`.

**Известные ограничения:**

- Ссылка `trycloudflare.com` меняется при каждом запуске и при восстановлении туннеля: её нужно вставить на сайт заново. Так же устроен Colab. Quick tunnel Cloudflare не даёт гарантий доступности.
- Каталог `models/controlnet` только отображается. Сам ControlNet по-прежнему загружается из Hugging Face через кэш, как в v1.7.0.
- Режим `gdrive` зависит от Google Drive: доступ по ссылке, лимиты на скачивание.
- Образ собирается на самом сервере, при первой сборке это несколько ГБ загрузок. Готового образа в реестре нет. Вариант с собственным образом на CloudCompute описан, но не проверен.
- Поддерживается только x86_64.
