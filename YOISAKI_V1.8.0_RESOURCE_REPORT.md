# YOISAKI v1.8.0 — RESOURCE REPORT

## Что реально измерено

Среда разработки: CPU, Python 3.12.14, PyTorch 2.6.0+cpu, Diffusers 0.36.0, Transformers 4.57.3, Accelerate 1.12.0, PEFT 0.18.0. `torch.cuda.is_available()` = false. Tesla T4 и полноразмерный pretrained Illustrious отсутствовали. **Чисел VRAM и производительности Colab/T4 в этом отчёте нет.**

В таблице — настоящие CPU-вызовы inference на маленькой случайной SDXL, 32×32 рабочих пикселя, 4 заданных шага, batch 1; image-режимы используют strength 0.5. Это проверка кода, а не качества, не benchmark реальной генерации и не прогноз памяти SDXL. Длительность включает CPU inference и очистку тестовой задачи. RSS относится к процессу Python вместе с зависимостями. Peak RSS — максимум выборок с интервалом 0.25 секунды, не точный пик аллокатора. Значения system RAM в исходном JSON относятся к хосту и включают другие процессы.

Исходные значения, включая null для CUDA: `validation/cpu-resources.json`. Первые операции прогревают runtime и библиотеки. Небольшая серия не доказывает отсутствие длительного накопления RAM. Подтверждены отсутствие нового набора SDXL-модулей при смене view, сохранение числа байт параметров и освобождение временных editor-view через weakrefs. Проверка storage pointers выполняется непосредственно вокруг `from_pipe` после снятия hooks: pointers не обязаны оставаться постоянными после CPU Offload и смены устройства.

## Устройство управления ресурсами

1. Одна существующая FIFO-очередь (`ThreadPoolExecutor(max_workers=1)`) обслуживает генерацию и ControlNet preprocessing. InferenceAdapter.lock остаётся дополнительной защитой; cleanup согласован с тем же lock.
2. Модель и VAE кэшируются по прежнему ключу checkpoint/VAE. Используются те же UNet, VAE, два text encoder и LoRA. Отдельная full SDXL для редактора не создаётся. `torch_dtype=None` предотвращает неявный перевод shared fp16 в fp32 при from_pipe.
3. CPU Offload, slicing/tiling VAE, allocator environment policy RAM FIX, прежний MemoryLog и opt-in Memory Profiler сохранены. `allocator_policy.py` побайтово совпадает с исходником.
4. EditorSession держит только нужные CPU-изображения/маски и небольшой выбранный контекст. Face Fix по умолчанию обрабатывает crop в 512×512, пользователь может явно выбрать другой рабочий размер. Итоговый исходник остаётся полноразмерным. Растушёвка вычисляется только в bounding crop маски.
5. Finally закрывает временные PIL images/masks, удаляет stage hook, возвращает plain base view и offload hooks. Большие conditioning tensors принадлежат завершившемуся стеку inference. Кэш модели и намеренно загруженные адаптеры сохраняются. Модель не перезагружается после каждого успешного задания.
6. Новых indiscriminate вызовов `torch.cuda.empty_cache()` нет. Сохранена существующая очистка кэша после освобождения wrapper/ControlNet. После получения результата работает ACK для v1.8, включая переподключение: это предотвращает накопление принятых PNG на диске движка.

## Допуск по бюджету

Измеряются доступная RAM (`/proc/meminfo`, с ограничением доступного cgroup v2 budget при наличии), RSS процесса, CUDA free/allocated/reserved и allocator peaks. Проверка учитывает доступную VRAM и свободную часть reserved pool; она отвергает только случаи, когда не помещается даже известный минимальный latent buffer. Для редактора проверяется нижняя граница совместно существующих исходника, результата, маски и рабочего RGB. Это **нижние границы**, а не доказанные оценки пиков активаций UNet, загрузки checkpoint или полного Python/Pillow heap.

Если измерения недоступны, они остаются null; приложение не объявляет ресурсную гарантию. При OOM пользователь получает ошибку и предложение явно уменьшить рабочий размер/batch или освободить память. Размер, steps, LoRA, seed и strength не уменьшаются автоматически. Неиспользованный ControlNet освобождается прежним механизмом перехода в base. Диагностические сбои получения CUDA-метрик не должны блокировать inference.

## Наблюдаемость

`memory.jsonl` сохраняет прежние phase-снимки, включая pipeline components, dtype/device и количество offload hooks. Новый вращаемый `resources.jsonl` содержит тип/длительность задачи, память до и после cleanup, allocator CUDA peaks, выборочный RAM/RSS peak, состояние загруженной модели до задания, факт reuse, тип реально использованного pipeline, число адаптеров, optional components после cleanup и исход cleanup. Максимум — текущий лог около 8 МиБ плюс previous. GPU measurements — реальные значения API PyTorch, когда CUDA доступна; CPU-тесты оставляют их null.

Последняя сводка доступна авторизованно через `/memory` (`job_resources`) и `/jobs/{id}` после cleanup. Запись в статусе может появиться чуть позже COMPLETED, поэтому для анализа используйте `/memory` либо скачанные логи. Последняя ячейка notebook скачивает текущие/предыдущие `memory.jsonl` и `resources.jsonl`. Изображения, промпты, access token/OAuth и содержимое исходников в ресурсные логи не записываются.

После прогрева сравнить RSS и allocated/reserved VRAM после cleanup; reserved отдельно от allocated может отражать кэш. Проверить отмену, невалидный запрос и следующий успешный job. Измерить полноразмерный Illustrious в реальных Colab RAM/VRAM. Данных для заявления об отсутствии CUDA OOM или долговременного накопления RAM на T4 пока нет.
