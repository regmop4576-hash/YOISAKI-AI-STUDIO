## 4. Расследование ошибок (каждая отдельно)

### 4.1 `ERROR: failed to solve`
Это сообщение BuildKit (`docker build`/buildx). Где его **нет**: скрипт `onstart` 1.7.5/1.7.6 никогда не вызывает `docker build`; в репозитории единственный запуск сборки образа (GHA run 40504927731) завершился успешно. Значит, сообщение пришло из процесса **на стороне CloudCompute**, который что-то собирает из `template_image`.
Воспроизведённый механизм (`docs/verification/v177/docker-manual-audit.log`): слой «bootstrap провайдера» поверх образа 1.7.5 (`FROM engine:1.7.5` + `RUN apt-get … openssh-server`) падает так:
```
E: List directory /var/lib/apt/lists/partial is missing. - Acquire (13: Permission denied)
ERROR: failed to build: failed to solve: process "/bin/sh -c apt-get update …" did not complete successfully: exit code: 100
```
Причина — `USER 1000:1000` в образе: инструкции bootstrap выполняются не от root. Второй реальный источник того же текста — нехватка диска: в песочнице сборка упала с `failed to solve … [Errno 28] No space left on device`. Что CloudCompute строит производный образ именно так — **не подтверждено** (скрипты bootstrap провайдера не опубликованы, документация недоступна из среды).

### 4.2 `Error response from daemon: No such container`
Возникает, когда `docker start/exec/inspect` обращается к контейнеру, который не был создан. В песочнице воспроизводится как следствие 4.1: образ не собрался → контейнер не создан → `docker start …` → `Error response from daemon: No such container`. В нашем образе нет Docker CLI, поэтому ветка «Docker-хост» в onstart внутри образа не срабатывает и источником быть не может. Вывод: согласуется с отказом bootstrap провайдера, но может иметь и независимую причину (например, отказ NVIDIA Container Toolkit при создании контейнера, см. 6.3). Не подтверждено для CloudCompute.

### 4.3 Инстанс #10758: CloudCompute «Running», YOISAKI «Instance initializing», «Terminal port has not yet been published by the host»
- Дефект сайта (подтверждён кодом): наблюдатель 1.7.5/1.7.6 переводил **любой непустой статус** провайдера в `INSTANCE_INITIALIZING` и не различал «инстанс работает» и «движок не отозвался». Исправлено (раздел 7).
- Сообщение о терминале означает, что bootstrap провайдера не опубликовал порт веб-терминала — т. е. bootstrap не завершился. Это согласуется с 4.1 (bootstrap не может работать от uid 1000) и с ситуацией, когда `onstart` вообще не выполнился.
- Без журналов инстанса точную причину для #10758 установить нельзя. Теперь приложение показывает статус провайдера как есть, через 15 минут молчания пишет «Инстанс работает, движок — нет», даёт проверить терминал и выгрузить диагностику.

## 6. Совместимость

### 6.1 Профиль bootstrap
Документированные значения (OpenAPI): `full`, `access_only`, `worker`, `none`. Тексты описаний профилей в снимке OpenAPI отсутствуют, живая документация недоступна. Решение:
- **по умолчанию `worker`**: образ YOISAKI сам запускает движок (CMD-супервизор), SSH/Jupyter не нужны, а маленький bootstrap оставляет больше места в общем лимите 16 384 байта;
- архитектура не зависит от того, выполняет ли профиль CMD образа: если выполняет — `onstart --provision` передаёт токен работающему супервизору; если нет — `--provision` запускает супервизор сам; гонка D2 устранена в обе стороны;
- `access_only`/`full` выбираются, если нужен веб-терминал; при `worker` недоступный терминал — ожидаемо;
- `provider_default` воспроизводит поведение 1.7.6 (поле не отправляется).
**Не подтверждено на реальном инстансе.** Первый запуск — приёмочный; при неудаче выгрузите диагностику и попробуйте `access_only`.

### 6.2 GPU и PyTorch (torch 2.10.0+cu128: sm_70 sm_75 sm_80 sm_86 sm_90 sm_100 sm_120, без PTX)

### 6.3 Драйвер и NVIDIA Container Toolkit
`NVIDIA_REQUIRE_CUDA=cuda>=12.8` базового образа заставляет NVIDIA Container Toolkit отказаться создавать контейнер на хосте с драйвером, поддерживающим CUDA < 12.8 (кроме веток 470/535/550/560/565, где действует исключение). Такой отказ выглядит как ошибка Docker при создании контейнера. Защита на сайте: фильтр по `cuda_max_good ≥ 12.8` (предложения с меньшей версией отклоняются; без версии — по умолчанию не подходят под фильтр «Только с указанной CUDA»). Сайт распознаёт в статусе провайдера `nvidia-container-cli … unsatisfied condition: cuda` и относит сбой к драйверу хоста.

### 6.4 Прочее
CPU Offload: accelerate 1.12.0 в образе, движок не менялся. Права: `/data` принадлежит uid 1000, токен 0600 в 0700. Постоянные данные: `/data` (VOLUME). Переменные окружения образа проверены (`YOISAKI_IN_IMAGE`, `YOISAKI_DATA_ROOT`, `YOISAKI_PYTHON`, `YOISAKI_CLOUDFLARED`, `HF_HOME`, `HOME`). Cloudflare Tunnel и ntfy.sh требуют исходящего доступа с инстанса — **не проверено**. Health: Docker `HEALTHCHECK` + `/health` через туннель; сайт ставит «YOISAKI ENGINE готов» только после успешной проверки состояния.
