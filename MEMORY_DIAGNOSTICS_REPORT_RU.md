# YOISAKI AI STUDIO v1.5.1 — отчёт о памяти

## Заключение и установленная причина

**Причина наблюдавшегося в Colab роста на 2,3 GB за дополнительную генерацию НЕ установлена. Устранение утечки SDXL на T4 НЕ подтверждено.** Исходные замеры пользователя: после первого Text2Img RAM 9,9/12,7 GB, после второго 12,2/12,7 GB; VRAM около 0,3/15 GB; Regional OFF. Python RSS и поэтапных замеров в этом наблюдении нет. Нельзя приписать весь прирост Python или CPU offload.

Подтверждённый источник накопления в исходном коде: готовые PNG оставались байтами в jobs. Это исправлено хранением на диске. В отдельном тесте 10 PNG этот механизм удерживал около 30 MiB, что НЕ объясняет гигабайты роста. Повторные unload/load одинаковых LoRA устранены как лишняя работа и риск фрагментации; их вклад в исходный рост RAM не измерен. При OFF без LoRA такой кэш не является объяснением проблемы.

## Минимальные исправления

- Один повторно используемый SDXL pipeline; fp16, model CPU offload, VAE slicing/tiling сохранены. Нет второго полного pipeline и переноса всей модели на T4.
- Кэш только текущего набора адаптеров по именам, путям, размерам и mtime. Изменение weight применяет веса без повторной загрузки. Смена конфигурации выгружает прежний набор; частичная ошибка загрузки освобождает pipeline. Regional routing не переписан.
- После завершения/ошибки/отмены закрываются PIL-изображения, снимаются временные hooks, освобождаются временные ссылки; вызывается gc после выхода из generate. Уже существующие offload handles освобождают GPU-компоненты. При полном unload удаляются hooks. empty_cache не вызывается после каждой генерации и не предлагается как лечение RAM.
- Idempotency сохраняет digest запроса вместо полного prompt/mask. Очередь и намеренные повторные отправки сохранены.
- Результаты атомарно записываются на локальный диск Colab, GET /results/{id}?index=N остаётся PNG API, ответ передаётся блоками 64 KiB. jobs хранит только метаданные.
- Сайт отправляет защищённый Bearer ACK только после сохранения всех изображений в локальную галерею. При ошибке ACK повторяется без повторной генерации; после reconnect восстанавливаются подтверждения сохранённых результатов.
- Удалена длинная полоса progress из JobProgress. Статус, ID, diffusion steps/процент, время, приблизительная ETA, очередь остаются текстом. Завершённые карточки свёрнуты по умолчанию. AMBER CORE, маски и остальные экраны не переработаны.

## Диагностика

Drive: MyDrive/YOISAKI_AI_STUDIO/diagnostics/memory.jsonl. При нестандартном model_root — diagnostics рядом с каталогом models. Фазы: before_model_load, after_model_load (также при повторном использовании), after_adapter_prepare, before_generation, after_decode, after_save, after_cleanup. Последняя фаза записывается и при ошибке/отмене активного задания. Отменённое до запуска задание не загружает модель.

Поля в байтах: system_ram_used_bytes (MemTotal − MemAvailable), system_ram_total_bytes, process_rss_bytes, cuda_allocated_bytes, cuda_reserved_bytes, cuda_peak_allocated_bytes, cuda_peak_reserved_bytes. Пики CUDA сбрасываются перед заданием. Есть число уникальных адаптеров, device/dtype UNet/VAE/двух text encoders, число offload hooks, pipeline_loaded, result_disk_bytes и result_ram_bytes. Последнее означает только постоянно удерживаемые PNG-результаты (теперь 0), а не нулевую память промежуточных PIL/tensors. System RAM включает другие процессы Colab; RSS включает CPU-веса, кэш и allocator. CUDA reserved не равняется физической VRAM в панели Colab.

Лог содержит только разрешённые технические поля и случайный job ID: без токенов, prompts, имён моделей и масок. Ротация: текущий файл около 8 MiB плюс один предыдущий. Ошибка записи Drive не прерывает генерацию: /health.memory_log_ok и защищённый GET /memory.log_write_ok показывают состояние. /memory возвращает последний sample. Сайт не выводит токены и не требует новых настроек.

## Хранение и ограничения

По умолчанию engine/.results на локальном диске Colab, либо YOISAKI_RESULTS_DIR. Индекс сохраняет результаты при перезапуске worker, пока сами файлы существуют. Квота 1 GiB; резерв 25 MiB на изображение и минимум 256 MiB свободного места сверх резервов. При нехватке места новое задание отклоняется HTTP 507; неполученные PNG не вытесняются. После ACK файл может удаляться через 24 часа; очистка при health/приёме нового задания. Галерея пользователя хранится отдельно и не очищается.

Неподтверждённые результаты не имеют принудительного TTL: ограничение диска обеспечивается отказом в новых заданиях. Это сознательно сохраняет требование не удалять изображение до получения сайтом. Полный сброс Colab всё равно уничтожает локальный диск. Сохраняется прежний лимит 100 записей заданий на сессию и 20 активных/ожидающих; после получения изображений и истечения TTL перезапуск очищает старую метаисторию. Сайт 1.5.1 принимает engine 1.5.0, но новые меры памяти/ACK требуют notebook 1.5.1.

## Сравнение до/после: только хранение PNG, НЕ diffusion

Два отдельных CPU-процесса, одинаковые 10 детерминированных случайных RGB-изображений 1024×1024, batch 1, без модели. Старый способ удерживает BytesIO PNG в списке, новый использует настоящий ResultStore. После каждого сохранения закрыт PIL и выполнен gc. Источник: tests/storage_benchmark.py (запуск python tests/storage_benchmark.py baseline и python tests/storage_benchmark.py disk). CUDA в этом тесте отсутствует; VRAM не измерялась.

## Реальные GPU-стресс-тесты: НЕ ПРОВЕДЕНЫ

CUDA/GPU и веса SDXL/Illustrious/Character/Style LoRA в среде проверки отсутствуют. Не проверены: 10 последовательных Text2Img OFF на одной модели; Character LoRA; две региональные Character LoRA; Style LoRA; фактическая RAM/VRAM T4; качество изоляции персонажей; работа Google Drive FUSE, настоящий Android/Termux и живой Cloudflare в Colab. Стенд браузера не заменяет устройство Android.

В notebook добавлена необязательная инструкция запуска engine/stress_memory.py через работающий реальный worker: 10 OFF, затем указанные LoRA-сценарии. Неуказанные ID пропускаются — для всех сценариев заполните character_id, second_character_id, style_id и triggers. Тест сохраняет настоящие PNG и after_cleanup RAM/VRAM каждого изображения на Drive в diagnostics/stress/summary.jsonl. Он не создаёт подставные изображения и не запускается без READY GPU engine 1.5.1. Начните с batch 1, 768×768, 20 шагов; затем повторите с исходным проблемным разрешением, одинаковым для всех 10 кадров. Не отправляйте одновременно задания сайта. При ошибке/таймауте тест останавливается, а не выдаёт успешный результат.

Сравнивайте after_cleanup RSS и System RAM после прогрева, число адаптеров/hooks, CUDA allocation/reservation по всем 10 итерациям. Рост должен стабилизироваться; устойчивый прирост требует дальнейшей диагностики. v1.5.1 предоставляет измерения и устраняет подтверждённое удержание PNG, но не гарантирует работу любой модели в 12,7 GB RAM. CPU offload сохранён; универсально безопасная замена для T4 без реальных замеров не заявляется. Граничное влияние между регионами и общие latents остаются ограничением регионального метода v1.5.0; идеальная изоляция не обещается.
