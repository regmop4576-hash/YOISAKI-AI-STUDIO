# YOISAKI AI STUDIO 1.7.4: настройка интеграций

Это продолжение исходного 1.7.3. Дизайн AMBER CORE и каталог engine/ сохранены. Версия сайта и CloudCompute-пакета — 1.7.4; протокол существующего движка — 1.7.0.

## Установка и обновление телефона

В существующей папке приложения:

```bash
bash update.sh ~/storage/downloads/YOISAKI_AI_STUDIO_V1.7.4_INTEGRATIONS.zip
./start.sh
```

Укажите фактический путь к скачанному ZIP. Для новой установки распакуйте архив в домашнюю папку Termux, откройте вложенную папку и выполните `bash install.sh`, затем `./start.sh`. Внутреннее имя папки `YOISAKI_AI_STUDIO_V1.4.0_LOCAL_EDITION` оставлено намеренно: его ожидает установленный update.sh. Оно не обозначает версию сборки. Готовый dist включён; повторная сборка на телефоне не нужна, если проверка целостности проходит.

Данные приложения находятся отдельно от исходников. Обновление сохраняет галерею, историю и настройки. Не удаляйте каталог данных приложения.

## CloudCompute API

GPU → CloudCompute → CloudCompute REST API → вставить свой `cc-…` → «Проверить и сохранить». Сервер проверяет ключ запросом GET `/instances`; отклонённый ключ не заменяет прежний. Ключ не попадает в localStorage, state.json, URL, диагностические сообщения или GPU. Он хранится в secrets.json с правами 0600 внутри закрытого каталога приложения 0700. Приложение слушает только 127.0.0.1; запросы требуют локальную сессию и проверяются по Host/Origin.

Реализованы:

- список и опрос статусов раз в 15 секунд при открытой странице;
- получение отдельного инстанса через локальный API;
- переименование через PATCH; локальный API также принимает label и expires_at;
- удаление с подтверждением ID;
- создание из конкретного offer/ask_id и опубликованного Docker-образа с подтверждением платной операции, размером диска и пределом цены в копейках RUB. Автоматический подбор выключен, strict_offer включён.

Для создания нужны действующий offer ID из панели и существующий опубликованный образ. Приложение не подставляет вымышленные предложения или образы. Сумму и условия проверьте в CloudCompute. Запросы создания/удаления не повторяются автоматически при таймауте: сначала обновите список в панели.

Документация: https://cloudcompute.ru/docs/api/index.html ; исходная OpenAPI-копия: `docs/api/cloudcompute-openapi-2026-10-27.yaml`.

В OpenAPI есть ошибка склейки: servers.url уже содержит `/api/v1`, а paths повторяет префикс. Используется один префикс: `https://app.cloudcompute.ru/api/v1/instances`. Без авторизации реальный маршрут вернул 401 `missing_api_key`, удвоенный путь — 404. Секретный ключ при разработке не использовался.

GPU Start/Stop/Restart в опубликованной спецификации отсутствуют. Одноимённые операции VPS относятся к другому ресурсу и не используются. Статус инстанса не означает готовность YOISAKI ENGINE: у генератора остаётся собственный HTTPS-адрес и токен. Удаление инстанса может удалить его диск.

Успешные ответы списка/деталей не имеют схемы в опубликованной OpenAPI. Адаптер принимает массив, data-массив, instances-массив или data.instances; неизвестный формат выдаёт CC_RESPONSE_SCHEMA и не помечается актуальным. Для подтверждения формата и платных операций необходим один реальный прогон с пользовательским ключом в приложении.

## Google Drive: настройка один раз для издателя

Для локального CLI-сервера применяется Google OAuth Authorization Code + PKCE с loopback redirect. Общий OAuth-сервер не требуется. Зарегистрированный **Desktop app** — публичный клиент: издатель может настроить клиент для сборки, а каждый пользователь авторизует собственный Google-аккаунт. Это не общий аккаунт Drive и не общий refresh token. Нельзя распространять Web application client secret этим способом.

В Google Cloud Console:

1. Создать проект и включить **Google Drive API**.
2. В Google Auth Platform настроить Branding (имя, support email, контакт разработчика), Audience **External**, Data Access — `https://www.googleapis.com/auth/drive.readonly`.
3. Для испытаний добавить нужные Google-адреса в Test users. В режиме Testing доступ ограничен тестовыми пользователями; refresh token для этого scope обычно истекает через 7 дней. Для публичного распространения потребуется настроить production consent и выполнить требования Google по проверке приложения и restricted scope. Смена статуса на Production сама по себе не означает прохождение проверки Google.
4. Создать OAuth client типа **Desktop app**. Для него loopback-порт динамический, callback приложения: `http://127.0.0.1:3000/` (при другом PORT изменится порт).
5. Скопировать `config/google-desktop-client.json.example` в `config/google-desktop-client.json`, указать зарегистрированные client_id и client_secret. Не добавлять туда access/refresh token. Перезапустить локальный сайт. Этот публичный Desktop client может быть включён издателем в свою сборку. Для индивидуальной установки те же поля можно сохранить в «Настройка OAuth» на сайте.

В поставляемом ZIP **нет зарегистрированного Google-клиента**. Приложение честно показывает, что он не настроен, и не рисует успешное подключение. Секретный ключ пользователя для разработки не нужен. Проверка браузерного возврата на Android/Termux и production consent Google остаётся обязательной после регистрации клиента.

Официальные основания:
- https://developers.google.com/identity/protocols/oauth2/native-app
- https://developers.google.com/identity/protocols/oauth2
- https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list
- https://developers.google.com/workspace/drive/api/guides/api-specific-auth

## Google Drive: обычное использование

1. Открыть **Модели** при любом выбранном провайдере, даже без GPU.
2. «Войти в Google» → выбрать свой аккаунт на странице Google → разрешить чтение → автоматический возврат в приложение.
3. «Выбрать папку» → открыть нужные каталоги → выбрать папку, содержащую `checkpoints/`, `loras/`, `vae/`. Поддержаны страницы списка и ввод ссылки/ID доступной общей папки. Сервер проверяет тип и доступность выбранного объекта через Drive API.
4. После подключения своего CloudCompute ENGINE нажать «Использовать на подключённом GPU». Доступ передаётся именно этому серверу по существующему защищённому каналу. Обновите CloudCompute-пакет до 1.7.4: старые серверы не умеют принимать root_folder_id.
5. В GOOGLE DRIVE AUTO SYNC нажать «Проверить модели», затем «Синхронизировать» либо выбрать отдельные модели. Сохраняются докачка, проверка контрольных сумм, пропуск установленных файлов и атомарная установка.

Токены сохраняются локально в secrets.json 0600; клиентские поля и токены не возвращаются браузеру. Refresh происходит на сервере при обращении к Drive и повторяется один раз после 401. На GPU существующий rclone обновляет свою копию самостоятельно. Выбранный root_folder_id записывается в rclone.conf 0600 и переживает перезапуск на том же диске. Пароль Google не вводится в студии. Команды `rclone authorize` и ручное копирование JSON-токена в новом интерфейсе не нужны.

«Выйти на телефоне» удаляет локальную копию. «Отключить Drive на GPU» удаляет копию на подключённом GPU. Для отзыва доступа у всех копий используйте Google Account → сторонние приложения. При смене аккаунта выберите папку заново и снова передайте доступ нужному GPU. Авторизация нового аккаунта не пересылает токены ранее подключённым серверам автоматически.

## Готовый Docker-образ и повторный запуск

Репозиторий содержит `.github/workflows/engine-image.yml`. После публикации исходников в своём GitHub-репозитории запустите вручную Actions → Build prepared YOISAKI engine. Workflow собирает имеющийся Dockerfile и публикует `ghcr.io/<owner>/<repo>/engine:1.7.4`. Выдайте стандартному GITHUB_TOKEN право Packages: write; для скачивания без авторизации сделайте пакет публичным. Workflow здесь не запускался; опубликованного образа пока нет.

На уже настроенном Docker-хосте:

```bash
YOISAKI_PREBUILT_IMAGE=ghcr.io/owner/repo/engine:1.7.4 ./start-cloudcompute.sh --mode docker
```

Подставьте реальный образ. Скрипт использует уже скачанный образ, скачивает отсутствующий, не запускает сборку PyTorch; `--rebuild` в этом режиме запрашивает образ заново. Compose сохраняет прежние bind mounts: постоянный YOISAKI_DATA_ROOT → /data. Для воспроизводимости можно указать digest опубликованного образа.

CloudCompute API принимает template_image, поэтому форма создания отправляет такой образ провайдеру. Однако опубликованная спецификация не задаёт управление volume mounts и не описывает, как template_image влияет на ENTRYPOINT/CMD и выдачу логов. До живого прогона нельзя обещать полностью автоматический первый запуск, постоянный /data или автоматическое получение ссылки движка через API. Первую конфигурацию образа/диска и чтение защищённой ссылки выполняют в веб-панели провайдера. Далее существующие сохранённое подключение, стабильный токен и rendezvous/named tunnel позволяют обычное повторное подключение без SSH, если они настроены. Клиент управления арендой не выдаётся за канал связи с движком.

Native-путь теперь проверяет готовый Python: совпадение всех требований, pip check и существующий import/CUDA-architecture check. Подходящее окружение переиспользуется без pip install; иначе остаётся частный venv и прежний кеш-маркер. Установка выводит фактические шаги pip; готовый Docker-путь — прогресс слоёв; существующий интерфейс подключения — стадии готовности движка. Проценты и ETA не выдумываются.

`.yoisaki-data-id` и содержимое models сохраняются при повторной подготовке каталога; это проверено тестами. Сохранность диска после остановки/пересоздания настоящего инстанса должен подтвердить провайдерский прогон с тем же volume: локальный тест не доказывает политику хранения CloudCompute.
